## 1. Introduction / 引言【全组统一写】

### 1.1 项目背景

写作指引：  
说明智慧教学服务系统为什么需要建设。可从大学教学活动中的基础信息管理、排课、选课、课程讨论、在线测试、成绩管理等痛点出发。

可写内容：
- 当前教学管理活动中的主要问题。
- 为什么需要一个统一的教学服务系统。
- AI 辅助选课等智能能力的引入背景。

### 1.2 项目目标

写作指引：  
用简洁语言说明系统完成后希望达到的效果。

建议覆盖：
- 为学生、教师、教务管理人员、系统管理员提供统一教学服务。
- 支持基础信息、排课、选课、讨论、测试、成绩的闭环。
- 提升教学服务效率、准确性和可维护性。
- 在智能选课等场景中引入 AI 辅助能力。

### 1.3.3 A 基础信息管理详细范围

基础信息管理子系统是 STSS 的基础支撑层。它不直接完成排课、选课、论坛、在线测试或成绩业务闭环，但负责维护这些业务所依赖的身份、组织、课程与权限数据，并通过统一认证、安全策略和日志能力保障其他子系统的访问可信度。

#### 1.3.3.1 包含范围

| 编号 | 范围 | 说明 |
|---|---|---|
| A-S-01 | 认证与会话安全 | 支持登录、登出、注册、当前用户信息获取、密码修改、忘记密码与重置、访问令牌刷新、活跃令牌查看与吊销；账号激活接口在代码中保留，但接口文档已标注为废弃能力，不作为核心验收入口 |
| A-S-02 | 用户基本信息管理 | 支持学生、教师、管理员等用户的创建、查询、编辑、软删除、批量创建、批量状态/角色调整、角色分配、密码重置与权限查看；用户创建、批量创建和删除由 `super_admin` 执行 |
| A-S-03 | 用户个人信息管理 | 支持用户维护个人资料、联系方式、头像和密码；头像上传限制为 JPG、PNG、WEBP，单文件不超过 5MB |
| A-S-04 | 院系与专业管理 | 支持院系、专业的新增、查询、编辑、删除与统计展示，并维护学生、教师、管理员与院系专业之间的归属关系 |
| A-S-05 | 课程基础信息管理 | 支持课程代码、名称、学分、学时、课程类型、开课院系、负责教师、考核方式、先修课程等基础数据维护；课程状态作为数据字段用于列表展示和筛选，当前接口不提供归档/恢复操作 |
| A-S-06 | 培养方案基础数据管理 | 支持按专业和年份维护培养方案、总学分、必修/选修学分、课程清单、建议修读学期等信息 |
| A-S-07 | 角色权限管理 | 支持角色、权限、角色-权限关系、用户-角色关系维护；当前接口访问控制以角色和本人/管理员规则为主，权限代码用于角色权限配置、聚合查询和后续扩展 |
| A-S-08 | 系统日志与安全审计 | 记录登录登出、用户变更、角色权限变更、院系专业变更、课程和培养方案变更等关键操作，支持按用户、操作、时间范围分页查询；当前令牌吊销接口不写入系统日志 |

#### 1.3.3.2 不包含范围

| 编号 | 不包含内容 | 说明 |
|---|---|---|
| A-O-01 | 学校统一身份认证真实接入 | 本项目仅定义和实现系统内认证，不负责接入真实 CAS、LDAP、企业微信等校级认证平台 |
| A-O-02 | 生产级入侵检测平台 | 系统需要记录安全相关日志并提供基础安全控制，但不建设完整的 SIEM、WAF 或入侵检测平台 |
| A-O-03 | 业务子系统核心决策 | A 组提供课程、用户、权限等基础数据，不负责自动排课算法、选课冲突判断、论坛内容审核、在线测试评分或成绩审核规则 |
| A-O-04 | 复杂数据同步 | 不负责与真实教务系统、人事系统、财务系统进行生产级双向同步 |

### 1.3.4 C 智能选课详细范围

C 智能选课子系统当前已挂载在 `/api/v1/course-selection`。后端以 A 组提供的用户、学生、教师、管理员、课程、培养方案和先修关系为基础，维护选课阶段、开课记录和选课记录；前端已提供学生、教师和教务管理入口。本文只按当前代码可见能力描述：AI 辅助已接入 OpenRouter，支持降级返回；连接控制仍为待完成项。

#### 1.3.4.1 包含范围

| 编号 | 范围 | 当前实现说明 |
|---|---|---|
| C-S-01 | 学生培养方案查看 | 学生可查看本人专业和年级匹配的培养方案、课程分组和建议修读学期；后端根据当前登录用户绑定的学生档案查询，不接受前端传入学生标识 |
| C-S-02 | 学分进展统计 | 学生可查看已选课程按课程类型聚合的学分进展；当前以 `ENROLLED` 选课记录和课程学分统计，公共课最低要求未在数据模型中完整表达 |
| C-S-03 | 课程与开课查询 | 学生可按关键词、课程类型、教师、开课状态等条件查询课程、开课列表、可选课程和开课详情 |
| C-S-04 | 选课事务 | 学生可在开放的选课阶段提交选课请求；后端执行容量、重复选课、时间冲突、最大学分、课程状态、开课状态、培养方案归属和先修课等校验，并使用事务控制容量扣减 |
| C-S-05 | 退课事务 | 学生可退选本人选课记录；当前退课要求处于第二轮或调整阶段，初选阶段退课确认策略仍为 TODO |
| C-S-06 | 选课结果与课表 | 学生可查询本人选课结果、汇总已选课程数和学分，并查看/打印本人课表 |
| C-S-07 | 教师名单与导出 | 教师可查询本人授课开课的学生名单，并可导出 Excel；后端校验开课教师归属 |
| C-S-08 | 选课阶段管理 | 教务管理员可创建、更新、查询选课阶段，校验时间范围、学期存在性和同学期同阶段活动时间重叠 |
| C-S-09 | 教务手动加课 | 学术教务管理员可为学生手动加课，要求填写原因，并记录系统日志；手动加课同样执行容量、重复、冲突和最大学分校验 |
| C-S-10 | AI 辅助选课入口 | 前端存在 AI 推荐页面，后端 `/ai-advisor/recommend` 与 `/ai-advisor/explain` 已接入并支持成功/降级返回；不产生推荐持久化结果，也不写入选课记录 |

#### 1.3.4.2 不包含范围

| 编号 | 不包含内容 | 当前状态说明 |
|---|---|---|
| C-O-01 | 真实 AI 推荐算法 | C6 已接入 OpenRouter 推荐链路，提供规则召回 + 模型生成 + 降级模板；当前仍不持久化推荐结果 |

### 5.2 安全需求

写作指引：  
A 组主写统一安全需求，各组补充本子系统权限点。

建议包括：
- 用户密码安全。
- 注册信息安全。
- 权限控制。
- 防越权访问。
- 系统日志。
- 防入侵管理。
- 成绩修改、选课管理等敏感操作审计。

#### 5.2.A A 组安全需求

| 编号 | 安全需求 | 验证方式 |
|---|---|---|
| NFR-A-S-01 | 用户密码不得明文存储或明文返回；注册、创建、重置和修改密码时，新密码至少 8 位且包含大小写字母和数字；登录失败、重置密码、修改密码等流程不得泄露敏感凭据 | 安全审查、接口响应检查 |
| NFR-A-S-02 | 访问受保护资源必须先完成身份认证；未认证请求应被拒绝 | 未登录访问测试 |
| NFR-A-S-03 | 系统必须实施认证、角色和本人/管理员关系控制；普通学生不得访问用户管理、角色权限、系统日志等管理功能 | 越权访问测试 |
| NFR-A-S-04 | 令牌刷新采用刷新令牌轮换机制；已使用、已吊销或过期的刷新令牌不得继续换取新访问令牌；密码变更、密码重置、用户删除、单用户角色分配或撤销应使相关刷新令牌失效 | 会话安全测试 |
| NFR-A-S-05 | 已实现审计范围内的关键操作必须记录系统日志，包括登录登出、认证模块密码变更、用户创建/更新/删除/状态变更、院系专业变更、课程和培养方案变更、角色与角色权限变更；用户角色分配、批量创建用户、令牌吊销和管理员重置密码当前不作为日志验收项；日志不得向普通用户开放 | 审计日志测试 |
| NFR-A-S-06 | 删除角色、撤销超级管理员关键权限、分配或撤销用户角色等高风险操作应校验操作者角色，并保护管理员自身关键角色不被误撤销 | 权限边界测试 |
| NFR-A-S-07 | 所有受保护接口应先完成认证；需要管理权限或本人限制的接口应在后端执行角色或本人/管理员关系校验，不得依赖前端菜单隐藏作为唯一控制手段 | 权限绕过测试 |
| NFR-A-S-08 | 系统应提供基础 Web 安全防护，包括受控跨域策略、安全响应头、统一错误响应和请求日志；这些能力用于降低常见误配置风险，不等同于生产级入侵检测平台 | 安全配置审查 |

### 7.6 F 成绩管理状态图【F 组填写】

建议对象：
- 成绩状态：未录入、已录入、修改申请中、已修改、已发布。
- 修改申请状态：已提交、审核中、已通过、已驳回。

#### 7.6.1 成绩状态

```mermaid
stateDiagram-v2
  [*] --> EMPTY: 学生完成选课并建立成绩占位

  EMPTY --> DRAFT: 教师首次保存成绩草稿
  DRAFT --> DRAFT: 教师继续编辑并保存草稿
  DRAFT --> SUBMITTED: 教师正式提交成绩

  SUBMITTED --> CONFIRMED: 管理员确认成绩
  SUBMITTED --> CONFIRMED: 改分申请审批通过并形成正式结果
  SUBMITTED --> SUBMITTED: 改分申请被驳回，原成绩保持不变

  CONFIRMED --> CONFIRMED: 改分申请审批通过并更新正式成绩
  CONFIRMED --> CONFIRMED: 改分申请被驳回，原成绩保持不变
```

| 状态          | 含义             | 允许的主要操作               |
| ----------- | -------------- | --------------------- |
| `EMPTY`     | 已有选课记录，但尚未录入成绩 | 教师录入成绩、保存草稿           |
| `DRAFT`     | 已保存成绩但尚未正式提交   | 教师继续编辑、保存草稿、正式提交      |
| `SUBMITTED` | 教师已正式提交，不能直接修改 | 教师或管理员发起改分申请；管理员确认或审批 |
| `CONFIRMED` | 已形成正式成绩        | 学生查询；教师或管理员发起受控改分申请   |

> “修改申请中”不作为 `Score.status` 的独立值，而由 `Score.modificationRequest` 是否存在表示。这样可避免成绩正式状态与审批流程状态混用。

#### 7.6.2 修改申请状态

```mermaid
stateDiagram-v2
  [*] --> 无申请: 成绩为SUBMITTED或CONFIRMED
  无申请 --> 待审批: 教师或管理员提交修改申请
  待审批 --> 已通过: 管理员审批通过
  待审批 --> 已驳回: 管理员审批驳回
  已通过 --> 无申请: 更新Score并清空modificationRequest
  已驳回 --> 无申请: 保留原成绩并清空modificationRequest
```

| 状态  | 含义            | 允许的主要操作          |
| --- | ------------- | ---------------- |
| 无申请 | 当前不存在待审批修改申请  | 授权教师或管理员可以发起新申请  |
| 待审批 | 已提交修改申请但尚未处理  | 管理员审批通过或驳回       |
| 已通过 | 申请已批准并写入正式成绩  | 查询修改日志           |
| 已驳回 | 申请被拒绝，原成绩保持不变 | 查询处理结果；之后可重新发起申请 |

#### 7.6.3 学生侧可见性规则

| 成绩状态        | 学生是否可见 | 是否参与统计      |
| ----------- | ------ | ----------- |
| `EMPTY`     | 否      | 否           |
| `DRAFT`     | 否      | 否           |
| `SUBMITTED` | 是      | 满足有效成绩规则时参与 |
| `CONFIRMED` | 是      | 满足有效成绩规则时参与 |

同一课程存在多条可见成绩时，系统选择总评成绩最高的记录作为有效成绩；总评成绩相同时，选择最近修改或录入的记录。

### 9.1 验证标准写法说明【全组统一写】

写作指引：
- 每条验证标准必须能被测试。

- 每条验证标准应追踪到功能需求和用户场景。
